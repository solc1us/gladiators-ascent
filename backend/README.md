# PostgreSQL + Prisma backend (Week 10)

The existing NestJS REST API now persists Gladiators in PostgreSQL using Prisma ORM 7.10.1. The controller, DTOs, response fields, and frontend API paths are unchanged. Node.js 20.19+, 22.12+, or 24+ is required (Node 24 tested).

## Setup and run

Run these commands from `backend/`:

```bash
npm ci
# Create .env from .env.example only if .env does not already exist.
# Set DATABASE_URL to your existing PostgreSQL database; never commit credentials.
npx prisma validate
npx prisma migrate dev
npx prisma generate
npx prisma db seed
npm run start:dev
```

The initial migration is committed, so a new checkout should apply it rather than create another initial migration. For deployment, use `npx prisma migrate deploy` instead of `migrate dev`. Development migrations may require permission to create a shadow database; never accept a reset prompt against a database containing data you need.

Environment variables are explicitly loaded from `.env` by the Prisma config, NestJS Prisma provider, and seed script. Run backend commands from `backend/`. Existing process environment variables take precedence. The `.env.example` contains placeholders only.

- API: `http://localhost:3000/gladiators`
- Allowed frontend origin: `http://localhost:5173`
- Build: `npm run build` (generates Prisma Client before compiling NestJS)
- Start compiled build: `node dist/main.js`
- `npm start` and `npm run start:dev` also generate Prisma Client automatically.
- Generated client code lives in `src/generated/prisma/`, is ignored, and must be regenerated after schema changes or a fresh checkout.

From `frontend/`, run `npm ci` and `npm run dev`. Build it with `npm run build`. No frontend changes are needed.

## Database behavior

`Gladiator` is the only application table. IDs are generated by PostgreSQL; they do not restart when NestJS restarts, and gaps are normal. GET all is ordered by ascending ID to retain the previous creation order.

The schema retains `name @unique`. The initial SQL migration also adds a unique index on `lower(name)` so concurrent requests cannot bypass case-insensitive name uniqueness. Keep this custom SQL index in future migrations. Service checks give friendly conflicts; Prisma P2002 and P2025 errors map to HTTP 409 and 404.

The seed uses names as stable unique identifiers, inserts records sequentially, and leaves existing records completely unchanged, including kills and status. It does not delete anything or run automatically on startup. Running it repeatedly keeps the same 11 seed names without overwriting progression. On an empty database, Marcus gets ID 11, preserving the frontend's existing initial selection. If an existing seed is renamed, its original name is no longer identifiable as that seed and a later seed run can recreate the original name. Existing databases need not have the same IDs as a fresh database.

## Verification

Manual REST Client requests: `requests/gladiators.http`. Use returned IDs, not an assumed next ID.

For automated integration verification, install frontend dependencies as well, leave port 3000 free, and run from `backend/`:

```bash
npm run build
node requests/verify-persistence.cjs
```

The script starts the actual compiled NestJS server, calls the frontend's actual Axios API functions, checks seeded names, CRUD responses, database contents, defaults, trimmed/case-insensitive names, DTO validation, missing IDs, and CORS. It restarts NestJS and checks that a uniquely named temporary record survives, then deletes that record only. It compares the final list against the original list to ensure unrelated data is unchanged. It requires the initial seed names to be present. Do not run against a database being actively modified by another process.

This checks the frontend API integration, not interactive browser rendering or gameplay. No profile, equipment, or gameplay progression persistence is added.
